# V64.3 verification report

This package updates the supplied V64.1 code, preserving its core ERP and approved visual structure. It does not deploy to GitHub/Vercel or change the live database. Testing used synthetic records in Chromium and PGlite (PostgreSQL), not production accounts.

## Parent actions

| Option | Implemented behavior |
|---|---|
| Student Profile | Selected child's details; correction request link |
| Attendance | Child-specific recent attendance and totals |
| Fee Details | Existing schedules/receipts, current due and fee notices |
| Exam Results | Published/locked result list; server-gated marksheet preview |
| Admit Card | Selected child's available/held cards and preview |
| Notices / Orders | General, class and individual notices; attachment links |
| Homework / Worksheets | Class AND section teaching/homework feed; attachment links |
| Gallery | Accessible school gallery; images/videos |
| Timetable | Selected class and section; day/bell order |
| Apply Leave | Date/type/reason form; validation, submit and history |
| Data Correction | Allowlisted fields; Admin approval request, never direct master overwrite |
| Transport | Existing route, vehicle, pickup, monthly fee and driver details |
| Gate Pass | Selected student's approval/exit/return history |
| ID Card | Existing official-card RPC and template; signed photo when available |
| Help / Complaint | Child-linked message to existing Admin Complaint Center |

All actions open a real section or form. Empty records display an empty state; query failures display an error/retry rather than false zero/false success. Profile, password and home controls remain available. Child pages use canonical admission linkage and server-side ownership checks, not name-based identity. Parent panel responses carry a navigation token so a late response cannot replace the next child's panel.

## Other corrections

- Deferred two early wrappers which referenced `adminCommandCenter` / `render` before their scripts loaded. These caused uncaught startup exceptions in the supplied source.
- Kept live global-state bridges from V64.2 and corrected mobile hidden-container rules.
- Fixed a minimum-width conflict that caused the sidebar to overlap content at laptop widths. Long menus scroll; long data tables scroll inside their own container.
- Teacher assignment API checks migration availability before Auth changes, uses one transaction for class/subject replacement, and accepts an academic session instead of forcing 2026-27. Password state is preserved on edits which do not change passwords.
- Handover transaction preserves responsibility/timetable snapshots, moves class/subject/timetable responsibilities, and deactivates the leaving profile. Ambiguous timetable identity aborts the transaction instead of guessing. Records are not deleted.
- Recursion-safe role helpers and profile-field guards protect role/status/student linkage. The patch does not increase PostgreSQL stack limits or disable all triggers/RLS.
- Native fee-notice printing uses measured A4 pages, one student per page, with client-only Preview → Print/Save PDF.

## Scope and remaining live verification

The current production schema, private triggers, data volumes, Auth settings, deployed RLS policies, storage permissions and credentials were unavailable. Local PostgreSQL fixtures verify the supplied migrations and targeted behaviors; they do not prove compatibility with every unknown production customization.

A remaining production `stack depth limit exceeded` error may originate in a custom Auth/staff/teacher synchronization trigger rather than the role helper. The read-only diagnostic SQL captures those definitions. No unknown trigger was disabled and no production security setting was weakened to hide an error.

Existing result/admit/official-card RPCs and fee calculators are retained dependencies. They were mocked for browser behavior, not rewritten or certified against real student results/ledgers. Calendar, salary, imports, transport generation and every historic ERP requirement were not fully exercised in this pass. This is not a certification that all prior requests are finished or that no future correction can ever be needed.

The Auth-service account operation and PostgreSQL provisioning cannot be one distributed transaction. Assignment writes are atomic; a later database failure after an Auth update is surfaced for retry rather than reported as success.

Use only `RUN-THIS-V64.3-SAFE-UPDATE.sql` for this update. Old SQL and installer notes are retained for historical reference, not an instruction to execute them. Validate on the actual database/Preview before production release.
